# Why HKDFGuard wraps keys with a device-held HMAC key

HKDFGuard derives each payload's wrapping key from the service's KEK with
HMAC-SHA-256, computed inside the TPM, HSM or secret-file provider that
holds the KEK. The design has three goals:

1. **Only something that can use the KEK can produce a payload that
   unwraps.** No public value lets anyone else mint one.
2. **Every payload has its own key.** A wrapping key that leaks opens one
   payload, not the service's history.
3. **Nothing a quantum computer breaks.** There is no public-key step, and
   every function is NIST-approved.

This document explains the construction, the threats it resists, and what
it does not protect against. The decision to adopt it is recorded in
[ADR-0001](adr/0001-post-quantum-wrapping-suite.md). It replaced the
pre-release ECDH construction described in [why-ecdh.md](why-ecdh.md),
which was never released.

## The construction

A service's KEK is a 256-bit HMAC-SHA-256 key. For every wrap:

1. Generate a random 32-byte `salt` and a random 12-byte AES-GCM nonce.
2. Build the payload header: every field before the ciphertext, in wire
   order -- version (`1`), provider tag, key-id length, key-id, salt,
   nonce, ciphertext length.
3. Ask the KEK's provider for two HMAC outputs, in one call. Each is one
   block of the NIST SP 800-108 counter-mode KDF with HMAC-SHA-256 as its
   PRF (`i = 1`, `L = 256`, integers big-endian):

   ```text
   fingerprint = HMAC(KEK, [1]_32 || "hkdfguard-kek-fingerprint-v1" || 0x00 || [256]_32)
   K_wrap      = HMAC(KEK, [1]_32 || "hkdfguard-wrap-v1" || 0x00 || Context || [256]_32)
   Context     = u16_le(len(service)) || service || header
   ```

4. Encrypt the DEK with AES-256-GCM under `K_wrap`, with the header
   followed by the fingerprint as associated data.

The payload stores the header, the ciphertext with its tag, and the
fingerprint. Unwrap rebuilds the same two blocks from the stored header,
gets both outputs from the provider in one call, compares the fingerprint
with the stored one, and decrypts.

Where the HMAC runs:

| Provider | KEK | HMAC |
|---|---|---|
| TPM 2.0 | A keyed-hash object (`HMAC_SHA_256`), generated by the TPM, `fixedTPM`, `fixedParent`, sign-only, with a random 32-byte authValue, in a key file under the storage root key | One-shot `TPM2_HMAC`, one per block, in a session keyed by the authValue |
| PKCS#11 | A 32-byte generic secret key generated on the token, sensitive, non-extractable, sign-only | Single-part `C_Sign` with `CKM_SHA256_HMAC` |
| External secret | The 32 raw bytes of the mounted secret file | In this library |
| Ephemeral | 32 random bytes in locked process memory | In this library |

## The threat: a forged payload

A forger's goal is a payload that the service accepts and unwraps to a DEK
**the forger chose**. If they manage it, they don't need to break any
encryption: the service encrypts its new data under a key the attacker
already knows. The way in is replacing a key file, or any other channel
that feeds bytes to `hkdfguard_unwrap_dek`.

The usual way to encrypt to a key someone else holds is public-key
encryption: ECIES, HPKE base mode, or a post-quantum KEM such as ML-KEM.
All of them let **anyone holding the public key** encrypt -- that is what
they are for -- so anyone holding the public key can mint a payload. Binding
more context into the key derivation doesn't help, because the forger
controls that context too.

Here there is no public key. `K_wrap` is an HMAC under the KEK, and HMAC
is a PRF: without the key, its output for an input not yet queried can't
be predicted. A forger who knows the wire format, a genuine payload's
header and the KEK's fingerprint still can't compute `K_wrap` for any
header, so any payload they build fails AES-GCM authentication. The
`without_the_kek_a_payload_cannot_be_forged` test builds exactly that
payload and checks it is refused.

## Why the key is different for every payload

The salt is in `Context`, so every payload's `K_wrap` is a different PRF
output. A wrapping key captured from one payload -- from a core dump,
swap, a debugger attached by the same user, or the bus of a discrete TPM
-- opens that payload and no other; HMAC outputs reveal nothing about the
KEK or about other outputs. With one fixed key per service, the same
capture would open everything the service ever wrapped.
`a_captured_wrapping_key_opens_only_its_own_payload` checks this.

## The fingerprint

The fingerprint is a fixed PRF output: the same for every payload a KEK
wraps, different for every KEK, and public. Being a PRF output, it reveals
nothing about the KEK. It does three jobs:

- **A clear error on the wrong KEK.** Unwrap compares it before
  decrypting, so a payload wrapped under a replaced or rotated KEK fails
  with `HKDFGUARD_ERR_KEK_FINGERPRINT_MISMATCH` rather than a generic
  authentication failure.
- **Identity for operators.** `hkdfguard provision` prints it,
  `hkdfguard_kek_fingerprint` returns it, `retire` requires it, and
  `[external_secret.pinned_keys]` pins it. For an external secret it can
  be computed from the file with OpenSSL; see
  [configuration.md](configuration.md).
- **Authenticated, not derived from.** It is in the AEAD's associated
  data, so changing it in a payload breaks authentication. It is not in
  `Context`: that is what lets the provider compute both outputs in one
  call (one key load on a TPM). `K_wrap` is keyed by the KEK, so it
  commits to the KEK's identity without it.

The labels differ and contain no zero byte, so a fingerprint block can
never equal a wrapping-key block, whatever the context.

## What is bound

| Input | Where it is bound |
|---|---|
| Service name | `Context`, length-prefixed so no two (service, header) pairs collide |
| Version, provider tag, key-id, salt, nonce, ciphertext length | `Context` and the associated data |
| Fingerprint | The associated data |
| Ciphertext | AES-GCM itself |

Changing any byte of a payload, or unwrapping it under another service's
name, makes unwrap fail. The `tampered_*` tests and
`the_wrap_block_binds_the_service_and_every_header_byte` change one field
at a time.

## Quantum computers

Nothing in the construction rests on a discrete-logarithm or factoring
problem, so Shor's algorithm doesn't apply. Grover's algorithm gives a
square-root speed-up against brute force: a 256-bit KEK and a 256-bit AES
key keep about 128 bits of strength, the level NIST counts as adequate
against quantum attack. Payloads harvested today, together with every
key file and public value on the host, stay safe.

On a discrete TPM, `TPM2_HMAC`'s output crosses the bus. It is protected
by the service key's authValue, a symmetric secret: the session's
parameter encryption and response HMAC are keyed by it, so a quantum
computer gains nothing there either (see
[ADR-0002](adr/0002-tpm-sessions-keyed-by-authvalue.md)). One step is
still classical. Provisioning sends the new key's authValue inside a
session salted to the storage root key by ECDH, as the TPM 2.0
specification defines. Someone who records that one command, and every
later session they want to read, and can later break P-256, could recover
those wrapping keys. Firmware and virtual TPMs (Intel PTT, AMD fTPM, cloud
vTPMs) have no external bus to record.

## Standards and FIPS 140

In short: **only NIST-approved functions, in an implementation that is not
FIPS 140 validated.** Don't describe a deployment as FIPS-compliant on
the strength of this library.

| Step | Algorithm | Standard |
|---|---|---|
| Wrapping key and fingerprint | HMAC-SHA-256 as the PRF of the counter-mode KDF | FIPS 198-1, SP 800-108r1 |
| Encryption | AES-256-GCM, 96-bit random IV, 128-bit tag | SP 800-38D (each key encrypts one DEK) |
| Salt, IV, generated DEKs | The OS random number generator (`getrandom(2)`) | -- |

The DEK is encrypted with AES-GCM, an approved authenticated-encryption
mode, rather than SP 800-38F key wrap (AES-KW); each key encrypts exactly
one DEK.

What isn't validated:

- **The software.** AES-GCM, and HMAC for the external-secret and
  ephemeral providers, run in this library using the RustCrypto crates,
  which are not a FIPS 140-3 validated module; nor is its random number
  source an approved DRBG inside one.
- **Most of the hardware this was tested on.** Intel PTT, AMD fTPM and
  SoftHSM2 are not validated. Many discrete TPMs and HSMs hold FIPS 140
  certificates, for particular firmware in a particular mode; a
  certificate covers what the device does, not what this library does
  with its output.

A FIPS claim would need the software crypto moved into a validated module
(for example `aws-lc-rs` in FIPS mode, or OpenSSL 3's FIPS provider) and
deployment on validated devices. The construction itself would not change.

## What it costs

- **Every wrap uses the KEK.** On a TPM that's a key load and two
  `TPM2_HMAC` calls per wrap and per unwrap. Wrapping can't happen while
  the provider is unavailable.
- **No wrapping from elsewhere.** A build server can't pre-wrap a DEK for
  a host; the host wraps it locally. That matches the deployment model:
  DEKs arrive from a pipeline and are wrapped on the host that will use
  them.
- **One-shot HMAC only, on a TPM.** Every input fits one `TPM2_HMAC`
  command (at most 352 bytes, against the 1024 the PC Client profile
  guarantees), so the provider never uses the `TPM2_HMAC_Start` sequence.
  On one Intel PTT firmware, that sequence put the TPM into failure mode
  until the next reboot.

## Alternatives considered

| Alternative | Forgery-resistant? | Quantum-safe? | Why not chosen |
|---|---|---|---|
| ECIES / HPKE base mode | No | No | Anyone with the public key can forge |
| ML-KEM, or another KEM | No | Yes | Anyone with the public key can encapsulate, so forge -- the same flaw as ECIES. TPMs that support it can't be counted on |
| ECDH against a hashed point (the pre-release design) | Yes | No | Shor's algorithm recovers the KEK from its public key, which a TPM key file stores in the clear. Not an SP 800-56A scheme, so no approved route either |
| Hybrid: HKDF over ECDH and HMAC outputs | Yes | Yes | Twice the keys and device calls, to hedge against HMAC-SHA-256 failing, which nothing suggests. The extra term needs its own justification |
| HMAC under SP 800-108 (chosen) | Yes | Yes | -- |

## What it does not protect against

- **Someone who can use the KEK.** On a TPM host that's any process that
  can open the device and read the service's key file and authValue file. Such a process can
  wrap any DEK it likes, legitimately. Against that threat, the protection
  is keeping who may use the KEK small, and `hkdfguard_open_file`'s
  refusal of key files that anyone else could have replaced.
- **Putting back an older genuine payload.** A payload carries no counter
  or epoch, so any payload this KEK ever wrapped for the service still
  unwraps, and a key file replaced with an older one is accepted.
  `hkdfguard_open_file` refuses key files that other accounts could have
  replaced, but not a rollback by the file's own owner (or root). Where it
  matters, record the payload's hash when it's deployed (the audit trail
  already logs `payload_sha256` on every unwrap) and compare it out of
  band.
- **A captured wrapping key, for its own payload.** Whoever captures one
  payload's `K_wrap` can open that payload, and can build a payload with
  that same header -- same salt and nonce -- that unwraps to a DEK of
  their choosing. Nothing else: not another payload, and not a payload
  with any other salt.

## Where it lives in the code

In [`src/crypto.rs`](../src/crypto.rs):

- **The SP 800-108 blocks:** `kdf_block`, `wrap_block`, `fingerprint_block`.
- **Wrap and unwrap:** `wrap`, `unwrap`, and `derive_keys`, the one
  provider call for both outputs.
- **KEK fingerprint:** `kek_fingerprint`.

The providers' `prf` implementations are in `src/provider/`; the TPM's
known-answer self-test is `validate_tpm_compatibility` in `tpm2.rs`.

Tests, in `crypto.rs` unless noted:

- **Known answers:** `every_protocol_step_matches_its_known_answer` pins
  the fingerprint, the wrapping-key block, the wrapping key, the
  ciphertext and a whole payload. The values were reproduced
  independently with Python's `hmac` module and pyca/cryptography, which
  share no code with this crate.
- **Forgery and isolation:** `without_the_kek_a_payload_cannot_be_forged`,
  `a_captured_wrapping_key_opens_only_its_own_payload`.
- **Binding:** `the_wrap_block_binds_the_service_and_every_header_byte`,
  `service_name_framing_is_unambiguous`, and the `tampered_*` tests.
- **The devices compute standard HMAC-SHA-256:**
  `tpm2_hmac_is_hmac_sha256_for_every_input_length` (`tpm2.rs`) and
  `token_hmac_is_standard_hmac_sha256` (`pkcs11.rs`), against software
  HMAC.
